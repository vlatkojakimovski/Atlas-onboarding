### 1. **`Atlas.Domain/Entities/Application.cs`** (Aggregate Root)

   - Domain-Driven Design with private setters and business methods

   - State transitions (Pending → Approved/Rejected)

   **Why:** Demonstrates how we coordinate the entire onboarding flow:
   - Parallel execution (verification + screening)
   - Error handling and resilience
   - Decision-making integration
   - Downstream actions (account, card)
   
   **Key method:** `ProcessApplicationAsync()` - the complete workflow

### 3. **`Atlas.Application/Validation/ApplicationValidator.cs`** (Business Rules)
   **Why:** Shows comprehensive validation logic:
   - Market-specific rules (national ID formats per Annex B)
   - Cross-field validation (documents, age, terms)
   - Clear error messages for API consumers
   
   **Key method:** `Validate()` and all the `Validate*()` helper methods

## 💡 The One Decision I Most Want to Be Asked About

### **"Why a Modular Monolith Instead of Microservices?"**

**Short answer:** Monolith-first is the pragmatic choice for a 3-day assessment with no actual load.



**What I built instead:**
- Clear separation of concerns (5 logical services)
- Interface-based design (easy to replace with HTTP clients)
- Retry policies already configured (Polly)
- Structured logging (Serilog → Seq)
- Repository pattern (abstracts data access)

**Alternative I rejected:**
Splitting into 5 separate API projects with HTTP communication would have:
- Consumed 1-2 days on infrastructure
- Required distributed transaction handling
- Made debugging harder
- Demonstrated Docker orchestration skills, not backend engineering judgment

**The trade-off:**
I sacrificed "looks like microservices" for "demonstrates solid engineering principles". I believe showing **why and when** to use microservices is more valuable than blindly implementing them.


## 🚫 What to Ignore

### 1. **Mock External Services**
   - `MockIdentityVerificationService.cs`
   - `MockSanctionsScreeningService.cs`
   - `MockCoreBankingService.cs`
   - `MockCardOrderingService.cs`
   
   **Why:** These are deliberately simple stubs. Real implementations would call external APIs. The interesting part is the **interfaces**, **retry policies**, and **how the orchestrator uses them**, not the mock logic itself.

### 2. **Migration Files** (`Migrations/` folder)
   - Auto-generated by EF Core
   - Schema is better seen in Fluent API configurations

### 3. **Contracts DTOs** (`Atlas.Api/Contracts/`)
   - Straightforward request/response models
   - No complex logic, just data transfer

### 4. **DependencyInjection.cs files**
   - Boilerplate service registration
   - Standard .NET configuration
